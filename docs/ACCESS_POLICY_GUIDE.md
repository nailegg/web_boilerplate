# 접근 정책 설계

모든 데이터에 사용자 소유권을 적용하지 않는다. 기능마다 데이터 공개 범위와 변경 권한을 먼저 정한다.

## 정책 유형

| 정책 | 의미 | 모델에서 주로 사용하는 값 |
|---|---|---|
| 개인 데이터 | 만든 사용자 또는 담당자만 접근 | `ownerId` |
| 공유 데이터 | 인증된 사용자가 함께 조회 | 소유자 필드 없음 또는 선택적 `createdBy` |
| 관리자 변경 | 일반 사용자는 조회하고 관리자만 변경 | `role`, 관리자 검사 |
| 조직 데이터 | 같은 조직에 속한 사용자만 접근 | `organizationId` |
| 공개 데이터 | 인증 없이 조회 가능 | 인증 검사 없음 |

`createdBy`는 누가 만들었는지 기록하는 감사 정보이며, 그 사용자만 접근할 수 있다는 뜻이 아니다.

## API 정책 작성 순서

각 리소스마다 다음 표를 먼저 만든다.

| 동작 | 인증 필요 | 허용 역할 또는 범위 |
|---|---:|---|
| 목록 조회 | 예/아니오 | 정책에 맞는 사용자 |
| 상세 조회 | 예/아니오 | 정책에 맞는 사용자 |
| 생성 | 예/아니오 | 역할 또는 조직 |
| 수정 | 예 | 역할 또는 소유권 |
| 삭제 | 예 | 역할 또는 소유권 |

실제 차단은 항상 서버에서 수행한다. 화면에서 버튼을 숨기는 것만으로 권한을 구현하지 않는다.

## 오류 규칙

- 로그인하지 않음: `401`
- 로그인했지만 권한 없음: `403`
- 대상이 존재하지 않음: `404`
- 입력값이 잘못됨: `400`

## 테스트 기준

과제에 따라 다음 테스트 중 필요한 것을 선택한다.

- 개인 데이터의 소유권 격리
- 공유 데이터의 공통 조회
- 관리자만 변경 가능
- 조직 단위 접근 격리
- 공개 API 접근
